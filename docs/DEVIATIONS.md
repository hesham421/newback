# Deviations from the erp-core execution plan

Every place where a step file was silent, wrong about the source, or impossible
as written, and what was done instead. Format:
`- [NN] <what was unspecified> → <what was chosen> (<why>)`. Earlier entries
bind later steps.

- [01] Acceptance runs the app against `docker run ... postgres:16` → used a natively installed PostgreSQL 16.15 (localhost:5432) with a fresh, empty scratch database `erp_step01`, dropped afterwards (Docker is not available on the execution machine; same major version, same empty-database condition).
- [01] Acceptance expects `GET /actuator/health` = `UP` with the `dev` profile → started with `--management.health.mail.enabled=false` (and `--spring.cache.type=simple`); without overrides the app starts and Flyway applies V1..V20, but overall health is `DOWN` solely because the `mail` indicator cannot authenticate to the default `smtp.gmail.com` with no credentials. Redis is not needed at startup (`management.health.redis.enabled=false` already). Making SMTP/Redis optional is step 02/03's job.
- [01] Step file says `PermissionConstants` holds 45 `PERM_FIN_*` constants → the source actually held 30; all 30 were deleted (the count in the audit was wrong; the goal is "none left").
- [01] Step file names `messages_en.properties` and `fin.*` keys → the English bundle is the base `i18n/messages.properties` and fin keys are `FIN-<status>-<CODE>`; the whole FIN block (header + 53 keys) was removed from `messages.properties` and `messages_ar.properties`. No `fin.*`/`app.fin.*` keys existed in `application*.properties`.
- [01] Non-fin code still mentioned FIN (OpenAPI `@Schema` examples `"FIN"`, `"FIN_JOURNAL_ENTRIES"`, `"Finance"`, and `PERM_FIN_*`/`com.erp.fin` in javadoc, test javadoc and the V19 SQL header) → `@Schema` examples switched to the NOTIF module (`NOTIF`, `NOTIF_TEMPLATES`, `Notification Service`), the `PERM_FIN`/`com.erp.fin` comments rewritten with a neutral `X_` example; purely historical provenance comments in `common`/`sec` (e.g. "REQ-FIN-015", "found by the FIN api-verify run") were left untouched (they are not code, data or references to the deleted package, and the README forbids reformatting unrelated code).
- [01] Renumbering leaves old version numbers inside file comments → every full file-name reference (`V<n>__<desc>`) in `src/` was rewritten to the new name; bare `V<n>` mentions in comments were left as written, and the old→new mapping is recorded in `src/main/resources/db/migration/README.md` and `docs/steps/01-report.md` (rewriting free-text history risks changing meaning; a mapping table is unambiguous).
- [01] Task 6 (delete fin lines from `CLAUDE.md`) → no edit made (`CLAUDE.md` contains no line listing `fin`/`FIN` as a module).
- [01] Task 7 (drop fin-only dependencies) → `pom.xml` unchanged (no dependency is used only by fin; `bucket4j-core` is unused by all code, fin included, so it is not fin-only and is kept — "keep if unsure").
- [01] `src/test/java/com/erp/architecture/CrossModuleBoundaryArchTest.java` listed `com.erp.fin` as a bounded module → entry and its javadoc paragraph removed (a module that no longer exists must not stay in the boundary list).
- [02] Acceptance "`mvn -q verify` green with Docker available" → Docker cannot run on the execution machine. The Testcontainers design is implemented as the primary path (`postgres:16`, `@ServiceConnection`, selected automatically when Docker is reachable), plus a Docker-free fallback: an in-process embedded PostgreSQL 16 (zonky `embedded-postgres` 2.1.0 + `embedded-postgres-binaries-bom` 16.4.0) chosen by `com.erp.testsupport.TestPostgres` when Docker is absent; `-Derp.test.db` / env `ERP_TEST_DB` = `testcontainers|embedded|auto` forces a backend. `mvn -q verify` was verified green on the embedded backend only. The Testcontainers path compiles, and forcing it here fails fast with a clear message, but it was not executed (orchestrator decision; preserves "tests run anywhere, no localhost services").
- [02] Task 1 names `org.testcontainers:postgresql` / `junit-jupiter` and `PostgreSQLContainer<?>` → Boot 4.0.1 manages Testcontainers 2.0.3, whose modules are `testcontainers-postgresql` / `testcontainers-junit-jupiter`; the non-deprecated class is the non-generic `org.testcontainers.postgresql.PostgreSQLContainer` (2.x renamed them; the old ids do not exist in the 2.x BOM).
- [02] Task 2 puts `@ServiceConnection` on a static container field of `AbstractIntegrationTest` → it sits on a `@Bean` in `TestcontainersPostgresConfiguration`, which `@Conditional` restricts to the Testcontainers backend and which returns the per-JVM static container held by `TestPostgres` (whose `stop()` is a no-op; Ryuk removes it at JVM exit). Boot resolves field-level `@ServiceConnection` unconditionally: it needs a non-null container and asks Docker for its image name, which would make Docker mandatory and rule out the fallback.
- [02] `AbstractIntegrationTest` must not name `ErpMainApplication` (acceptance), and Boot's upward `@SpringBootConfiguration` search from `com.erp.sec` never reaches `com.erp.main` → added the test-side `com.erp.ErpTestApplication` (same composition: scans `com.erp` and excludes `HibernateJpaAutoConfiguration`; filters out other `@SpringBootConfiguration`s), named explicitly by the base class. An upward-discoverable class in `com.erp` would not work, because the search scans recursively and would find two configurations.
- [02] Task 5 annotates the two `DownloadTokenStore` implementations with `@ConditionalOnBean`/`@ConditionalOnMissingBean` → the annotations are on the classes as written, but they are registered by a new `com.erp.file.config.DownloadTokenStoreAutoConfiguration` (listed in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, ordered after `DataRedisAutoConfiguration`, importing Redis first, then in-memory) instead of being component-scanned. A component-scanned `@ConditionalOnBean` is evaluated before any auto-configured bean exists, so the Redis store would never be picked.
- [02] Task 5 says Redis is used by "`FileAccessTokenDomainService`/file service" → only `FileService` used `StringRedisTemplate`; it now uses `DownloadTokenStore`. `FileAccessTokenDomainService` (AES/GCM crypto only) is unchanged.
- [02] Task 3 says only that `spring.data.redis.*` is absent → the test profile also excludes `DataRedisAutoConfiguration`, `DataRedisReactiveAutoConfiguration` and `DataRedisRepositoriesAutoConfiguration` (Boot creates a `StringRedisTemplate` whenever spring-data-redis is on the classpath, whatever the properties say; without the exclusion the Redis token store would be selected and would try `localhost:6379`). The mail block also disables SMTP auth/STARTTLS, sets 1 s connect/read timeouts and turns off the mail health indicator, so the absent server fails fast.
- [02] `NO_MAIL_SENDER` → a public constant on `DefaultChannelProvider`, returned as `ChannelSendResult.failure(NO_MAIL_SENDER)`, which `DispatchService` stores as `NOTIF_LOG.errorMessage` with status `FAILED`. It is a recorded failure reason, not a thrown `LocalizedException` code, so it has no `NotifErrorCodes` entry or i18n message. Note: the test profile keeps `spring.mail.host`, so the `JavaMailSender` exists in tests (as Task 3 requires) and `NO_MAIL_SENDER` appears only when no mail host is configured; unit-tested directly.
- [02] `SecReadOneIntegrationTest` autowires `DevPasswordResetSupportService`, which is `@Profile("dev")` ("must never be given one in any other profile"), and tests may not use `dev` → the test imports a nested `@TestConfiguration` that defines the same class as a test-only bean (same `@Transactional`/`@PreAuthorize` proxies). Production gating and every assertion are unchanged, and the dev controller stays absent in tests.
- [02] `UserRolesInResponseIntegrationTest` declared `@SpringBootTest(properties = "...generate_statistics=true")` → moved to `@TestPropertySource(properties = ...)`, because subclasses must not redeclare `@SpringBootTest`.
- [02] Task 6 `reuseForks=true` → set. The existing `windows-tests-no-fork` profile (forkCount=0) is kept, so on Windows the tests run inside the Maven JVM and `reuseForks` has no effect there. `-Dtest=` filtering verified.
- [02] Tests beyond migration → added unit tests for the step's new code only (`InMemoryDownloadTokenStoreTest`, `DefaultChannelProviderTest`, `DownloadTokenStoreAutoConfigurationTest` for both Redis/no-Redis branches) and `TestProfileWiringIntegrationTest` (PostgreSQL 16, not `localhost:5432`, no Redis template, in-memory store, Flyway history clean), per README §4's per-step minimum. These are not new tests for existing untested modules (out of scope).
- [02] Embedded PostgreSQL on a Cp1256 Windows host → the zonky builder pins `encoding=UTF8` and `locale=C` for initdb, so Arabic seed data is stored correctly whatever the OS code page.
