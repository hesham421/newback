# erp-core 1.0.0 — governed API test plan (`TC-CORE-*`)

## 1. Scope

This plan covers the **new HTTP-observable behaviour** that steps 01–12 of `erp-core-plan/` added to
`erp-core` and `erp-app-reference`, run as black-box HTTP cases against **one running reference app**.

- **In scope:** tenancy and provisioning (05); the STAFF/CUSTOMER realms and the permission catalog (06);
  file storage and public URLs (07); asynchronous notifications and the inbox (08); the number-series
  admin API and settings scopes (09); the generic audit log (10); reporting (11). Also the platform
  surface that steps 01–04 changed: no `fin`, auto-configured public paths and OpenAPI groups, and the
  bootstrap admin.
- **Out of scope:** behaviour that existed before step 01 and that no step changed (for example SEC
  role/grant CRUD semantics and MDL lookup CRUD). These appear only as fixtures.
- **Not reachable over HTTP:** in-process APIs (`NumberSeriesApi`, `SettingsApi`, `AuditApi`), startup
  failures, schema rules, ArchUnit rules, CI. §9 lists each one with the JUnit test that covers it.
  No HTTP endpoint is invented for any of them.

**Sources of truth.** Every expectation below comes from one of these:
- `erp-core-plan/NN-STEP-*.md` (`§Tasks`, `§Acceptance`);
- `docs/steps/NN-report.md` (where it differs from the step file, the report wins: for example
  `PATCH /api/v1/files/{id}/visibility` instead of `/api/v1/file/documents/{id}/visibility`);
- `docs/DEVIATIONS.md` and `docs/CONSUMING.md`;
- the live OpenAPI document (`GET http://localhost:7272/v3/api-docs`, read 2026-10-05);
- the controllers, DTOs, `*ErrorCodes`, `GlobalExceptionHandler`, `SecSecurityErrorHandler`,
  `TenantResolutionFilter` and `RealmEnforcementFilter` sources under `erp-core/src/main/java/com/erp/`
  and `erp-app-reference/src/main/java/com/erp/app/`.

The `covers` column cites these with the following abbreviations:
- `NN-STEP §Acceptance bK` is bullet K of the step's Acceptance section; `NN-STEP T<k>` is Tasks item k.
- `NN-report` is the step report, cited with its section name.
- `NN-report dev N` is decision/deviation N in that report, which mirrors `docs/DEVIATIONS.md`.
- `JUnit:` names the existing test the case mirrors.

### 2.1 Run profiles

Most cases run against the app as it is already running (**P-LIVE**). A few behaviours cannot be
reached in P-LIVE and need a restarted variant of the app:
- a delivered e-mail;
- a customer token, obtained the legitimate way: the verify token reaches the customer only by e-mail,
  and only its SHA-256 hash is stored (06-report Summary; `CustomerAccountService`);
- a failing mail server;
- a lowered export cap.

> **Fixed defect (history), never a test path.** v1.0.0 had a second way to get a customer token in
> P-LIVE: a staff admin could `DELETE /api/v1/sec/users/{customerId}` (deactivate has no state guard, so
> `PENDING_VERIFICATION` became `DISABLED`) and then `PATCH /api/v1/sec/users/{customerId}`
> (`assertCanReactivate` only requires `DISABLED`, so the row became `ACTIVE`), after which the unverified
> customer could log in. That bypassed the e-mail verification step 06 requires and let staff user
> management act on CUSTOMER rows — a realm-isolation / verification-bypass **defect** (review round 1,
> orchestrator decision). SEC-028..030 asserted the correct behaviour and FAILED against v1.0.0 (phase-D
> api-verify run `2610050236DB`). The fix (`docs/DEVIATIONS.md` `[14]`, superseding 06-report dev 6 for
> by-id management, search, sessions and the dashboard) makes the staff side of SEC STAFF-realm only: a
> CUSTOMER id on any staff by-id endpoint answers 404 `SEC-404-USER`. SEC-028..030 are now expected to
> PASS; SEC-031..033 add the search, session and dashboard parts. P-MAIL stays the only sanctioned way to
> obtain a customer token.

The database persists across restarts. Run each profile after the P-LIVE phases with a fresh `RUN`
suffix. In-memory download tokens and rate-limit buckets do not survive a restart.

### 2.2 Notation

- **Headers.**
  - `A:T_X` is `Authorization: Bearer $T_X`.
  - `TC:X` is `X-Tenant-Code: X`.
  - `AL:ar` is `Accept-Language: ar`.
  - JSON bodies are sent with `Content-Type: application/json`.
- **Success envelope** (`com.erp.common.web.ApiResponse`):
  `{"success":true,"data":…,"timestamp":"…"}`. "200 · `data.x`=v" means status 200, `success=true`
  and `data.x == v`.
- **Failure envelope** `E(CODE)`: `{"success":false,"error":{"code":"CODE","message":"<localized>","fieldErrors":[{"field","message"}]?},"timestamp":"…"}`.
  `fieldErrors` is non-null only for validation failures; otherwise it is serialized as `null` (`GlobalExceptionHandler`). The filter-level
  refusals emit the same envelope by hand, without `fieldErrors`. They are:
  - `TENANT_REQUIRED`, `TENANT_NOT_FOUND`, `TENANT_SUSPENDED` from `TenantResolutionFilter`;
  - `SEC-401-INVALID-CREDENTIALS` and `SEC-403-FORBIDDEN` from `SecSecurityErrorHandler`;
  - `REALM_MISMATCH` from `RealmEnforcementFilter`.
- **Which 403 code.**
  - A `@PreAuthorize` denial inside a `com.erp.sec.service` class answers `SEC-403-FORBIDDEN`
    (`SecForbiddenAdvisor`).
  - The same denial in any other module answers `ACCESS_DENIED` (`GlobalExceptionHandler`).
  - A filter-chain denial answers `SEC-403-FORBIDDEN`.
- **Page.** `data` is a Spring `Page`: `content[]`, `totalElements`, `number`, `size`, …
- **JWT claims** are read by base64url-decoding the token's payload segment (test-side only).

- Every created code, username and e-mail carries `{run}`, so re-runs never collide and never touch seed data.
- Reference data is created in a provisioned tenant (A) unless a case needs PLATFORM. The exceptions are
  SEQ-001, which deliberately proves the provisioning copy, and SETTINGS-001/003. Provisioning copies
  PLATFORM's lookups, templates and series to every later tenant (10-report Notes).

- Tenant C is the only tenant ever suspended, and TENANT-024 re-activates it.
