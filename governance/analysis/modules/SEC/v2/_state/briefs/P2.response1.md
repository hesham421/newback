**Decision you should look at: ADR-SEC-035 (accepted as non-breaking)**
- The profile requires every primary key to come from a named sequence, with only one strategy in the database. v1 built all 13 of its keys as identity columns instead.
- So this migration moves all 14 tables onto `SEQ_{TABLE}` sequences. It creates each sequence, sets it to continue after the highest existing key, then removes the identity. No key values or names change.
- **Deployment consequence:** the database no longer generates keys. The v2 backend must take each new key from its sequence, and it must be deployed together with this migration. The current v1 backend's inserts would fail against the migrated schema.
- **Unverified assumption:** the profile says the real database already builds its keys on named sequences. If the `SEQ_SEC_*` sequences already exist there, the 13 `CREATE SEQUENCE` lines for the v1 tables will fail and should be skipped. I didn't check the real database or the backend repo, because the brief limits me to its own inputs.
