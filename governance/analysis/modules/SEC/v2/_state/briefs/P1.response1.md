## The blocking conflict (ADR-SEC-031)
The P0/P0.5 decisions fixed the Oracle consumer's role as: FIN module grant + journal-entry screen grant + create action, and **no VIEW grant** (business-policies decision #4, ADR-SEC-018, ADR-SEC-030). SEC v1 won't allow that role:
- **At grant time:** under REQ-SEC-030 / RULE-SEC-007 (the profile's `gateway_action: VIEW`), granting any action other than VIEW without VIEW on the same screen is refused with `SEC-409-NO-VIEW-GRANT`.
- **At request time:** the interceptor denies the call with `SEC-403-FORBIDDEN`.
- **FIN v2** relies on the same rule.
- **Acceptance 2** and POL-SEC-012 say this invariant is inherited by service accounts, not reopened.

As decided, the daemon's first journal-entry call would fail, which is exactly the break this change set exists to prevent. Every way out contradicts something already approved, which is why it's BLOCKED rather than an ADR I could settle myself. The options:

- **A — count VIEW as part of the required path (recommended).** Only the wording of decision #4 and ADR-SEC-018 changes. The cost is that the daemon can also read FIN journal entries.
- **B — exempt service accounts from the VIEW rule.** This is a breaking change to REQ-SEC-030 / RULE-SEC-007.
- **C — change the platform-wide VIEW convention.** This affects every module.
- **D — a FIN-side intake page whose VIEW exposes no data.** This is the only option that keeps "nothing else" literally true, but it needs a new FIN change set.

The delta takes no side: no acceptance criterion asserts the consumer's exact grant set. Once you pick an option, the change is one AC (A or D) or a re-run of P1 (B).
